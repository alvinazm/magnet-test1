# Magnet 出题工作流(通用 SOP · 可跨领域复用)

> **用途**:把出题从选题到提交的全过程固化成可复用流程。**与题材无关**——无论是零售门店分析、
> 人力薪酬复核、财务审计、供应链对账还是合同审阅,环节与闸门完全相同,变化的只是"口径"和"探针"。
> **依据**:`docs/skill/rules1.md`(「Magnet」出题专家培训文档 v3.0)、`docs/skill/rules2.md`(要点摘要)、
> 根目录 `AGENTS.md`(引用规范)。
> **配套脚本**:材料生成器、`docs/skill/data-validation.py`(L1–L5 自检)、
> `docs/skill/validate_a_module_levels.py`(A 模块档位机审)、`docs/skill/validate_all.py`(统一入口)、
> Solution 生成器。
> **怎么用这篇文档**:
> · **第 0 节**=每个项目、每个环节开工前都要做的"读培训文档",这是本流程的起点;
> · **第一篇**=通用骨架,任何领域直接照做;
> · **第二篇**=换领域时的 6 步实例化手册(本篇才是"复用"的关键);
> · **第三篇**=本项目(零售门店题)的落地实例,只作参照,下个题目可整段替换。
> **版本**:v2.1(2026-09-24;v2.0 拆分通用骨架与领域实例,本版新增"培训文档阅读"作为前置与贯穿动作)

# 第一篇 · 通用流程(与题材无关)

## 2. 逐环节 SOP

### 环节 0 · 通读培训文档(强制前置动作)

**做什么**:项目**开始前**通读一遍培训文档,建立全局认知;此后**每个环节开工前**复读该环节对应的章节;
**提交前**再按章节逐条对照自检一遍。

| 时点 | 动作 | 为什么 |
| --- | --- | --- |
| 项目开始前 | 通读 `docs/skill/rules1.md` 全篇(一~七章),用 `docs/skill/rules2.md` 做要点校对 | 培训文档规定的是判据来源,不看就开始设计,后面必然返工 |
| 每个环节开工前 | 只复读该环节对应的章节(见下表),带着该环节的具体问题读 | 逐环节复读比一次性通读有效,能把条款直接落到当下动作 |
| 提交前 | 按章节逐条对照(第四、五、六、七章) | 机审只看形式,条款对照才看实质 |

**必做记录**:记下 `docs/skill/rules1.md` 的版本号与最近几条更新日志。培训文档是**持续迭代**的
(v2.2 明确专家无需自行脱敏、v2.4 把"场景描述"改为"任务说明"、v3.0 改了模块 B 口径并调整附件要求),
版本差异本身就是风险源——本项目就踩过一次:**旧版任务书要求"异常编号(A-001、A-002…)",
新版删除了该要求,导致对模型产物的判定依据前后不一致**。

**环节 ↔ 培训文档章节对照表**:

| 环节 | 必读章节 | 通读时要回答的问题 |
| --- | --- | --- |
| 1 选题与场景 | 一、这个项目在做什么;二、3 个质量重点;三、产线任务流程总览;4.1 先从真实工作中选任务 | 这是真实岗位会发生的工作吗?核心事实与规则是否都在题内?难度是来自专业判断,还是来自故意缺信息? |
| 2 材料设计 | 4.3 附件怎么准备(文件类型多样性及例外、附件基本要求、真实性与内容卫生、脱敏与合规、无嵌套格式) | 附件数量与类型是否达标?有没有出题视角残留?是否解释了单一类型的例外理由? |
| 3 材料自检 | 4.3 附件的基本要求;七、题目状态与退回规则 | 机审会查什么?退回后只能改哪些内容? |
| 4 任务说明 | 4.2 任务说明怎么填(含预计任务耗时口径、附件分类、交付物要求、不要写的内容) | 六个字段是否都齐?有没有写出实际答案或异常名单? |
| 5 Query 定稿 | 5.1 最终 Query 应讲清楚什么;5.2 怎样注入专业领域知识;5.3 简单与专业 Query 对比 | 七要素是否齐?企业专属阈值、资格条件、来源优先级是否都有题内依据? |
| 6 三模型与评估表 | 六、阅读 M1/M2/M3 并填写评估表(6.1 A/B/C 分工、6.2 A 写法、6.3 A 元数据、6.4 可追溯性、6.5 模块 B、6.7 模块 C) | A 的条数与类型分布达标吗?类型按"主要失败对象"判了吗?B 的证据是否写到"原文 + 文件名 + 位置"? |
| 7 专家 Solution | 7.3 Solution 提交(含 Solution 是什么/不是什么、质量要求、与评估表的关系) | Solution 是"可交付成果"还是"说明我准备怎么做"?有没有混入评测视角内容? |
| 8 提交与审核 | 7.1 题目状态表;7.2 不通过或人审退回时 | 每个状态能改什么、退回去向是什么? |

**正确性保障**:这一节的产物不是文档,而是"**判据来源已确认**"这一状态——任何后续环节出现争议时,
以培训文档条款为准,而不是以个人习惯或上一道题的做法为准。

### 环节 1 · 选题与场景设计

> **开工前必读**:`docs/skill/rules1.md` 第一章、第二章、第三章、第 4.1 节。

**做什么**:用一句话回答——"在什么业务情境下,哪个岗位会使用哪些材料,完成哪些专业处理,
最后交付什么文件,供谁做什么决策"。合格场景须同时具备:明确的业务发起原因、真正要用到的材料、
至少一个会影响结论的专业判断点、清晰的最终交付物、结论能回到附件的事实与规则、出题人自己能说明
如何验证。

**正确性保障(闸门 0)**:把"我想要的效果"写成机器可判的断言,写进自检脚本 L4/L5。
**必须是 `check()` 而不是 `print()`**——看得到但不判定,等于没检查。

### 环节 2 · 材料设计

> **开工前必读**:`docs/skill/rules1.md` 第 4.3 节(附件怎么准备:文件类型多样性及例外场景、附件的基本要求、
> 真实性与内容卫生、脱敏与合规、无嵌套格式)。

**做什么**:写生成器一次产出全部附件;每个数值只能有一个生成来源。

**正确性保障(六条通用规则,前五条为强制约束 C-1~C-5)**:

1. **单一事实源**:同一指标只在一处生成,其余表由它派生;
2. **固定随机种子**:保证可复现(本项目 `SEED = 42`);
3. **改参数不打乱随机流**:调整随机区间时保持随机数**调用次数**不变,否则整份数据漂移
   (实测:只改区间 → 9 个附件里 8 个逐格不变;改成硬编码日期 → 全库变化);
4. **汇总必须由明细派生(C-1)**:凡题包内同时存在某业务的**明细表与汇总表**,汇总值必须由明细表
   按"主键 + 期间"聚合得出,**禁止独立随机生成**。这是最容易被忽略、后果最严重的一条——
   本项目 D1 即为此类:同一渠道、同一 SKU 集合、同一日期区间,活动明细 **42 件 / 46,715.52 元**
   vs 订单台账 **2 件 / 186.72 元**(中位比 0.042),导致促销口径无法被订单台账复核;
5. **无明细时允许直接生成,但必须登记并声明(C-2)**:某指标确实没有明细来源时(如门店人力费用、
   水电、折旧摊销、到店销售额、履约费),**允许直接生成汇总值**,但必须同时满足三点:
   ① 在自检脚本的汇总矩阵中登记为"原始汇总值";② 在制度或《异常与待核清单.xlsx》中声明其
   "只到汇总级、不可独立复算";③ 不把它当作需要独立验证的核心结论的唯一依据。
6. **改动必须做基线回归(C-5)**:每改一次生成器,都要与上一版材料做逐 Sheet 比对,
   确认"**实际变化 ⊆ 预期变化**"。本项目曾因调整促销生成逻辑时无意改变随机数调用顺序,
   导致 9 个附件全量漂移,只能靠人工逐格比对才发现;现在由 `validate_baseline.py` 自动完成:
   `--expect "文件名"` 只允许指定文件变化,超出即失败;确认无误后 `--update` 更新基线。

**汇总—明细可复算矩阵(每个汇总字段都必须归入三类之一)**:

| 类别 | 含义 | 验证方式 |
| --- | --- | --- |
| ① 明细聚合 | 能由明细表按"主键 + 期间"复算 | L3 跨文件勾稽 |
| ② 行内派生 | 能由同一行其他列按公式算出 | L2 单文件公式自洽 |
| ③ 原始汇总值 | 无明细来源,允许直接生成 | 必须登记 + 声明(R-12) |

**一句话判定法**:把明细表删掉,这个汇总值**还能被解释吗**?能→① 或 ②;不能→③,必须声明。
脚本侧由两条探针兜底:**R-11** 检查"是否有汇总字段未登记来源",**R-12** 检查"③ 类字段是否已声明",
未登记或未声明的一律记入风险登记。

### 环节 3 · 材料自检(L1–L5)

> **开工前必读**:`docs/skill/rules1.md` 第 4.3 节"附件的基本要求"与第七章"题目状态与退回规则"
> (明确机审查什么、退回后只能改什么)。

| 层 | 问的问题 | 通用内容 |
| --- | --- | --- |
| L1 | 文件与字段是否完整 | 附件数量、表头、唯一键、非空、枚举合法 |
| L2 | 单文件公式是否自洽 | 派生字段 = 其定义式 |
| L3 | 跨文件勾稽是否成立 | 主键、聚合口径、规则复算 |
| L4 | 业务是否合理 | 量级、相关性、规则可判定性 |
| L5 | **换个口径读会不会得出另一个答案** | 跨口径反证探针(见第 4 节探针库) |

**命令**:

```bash
.venv/bin/python docs/skill/data-validation.py                          # 默认:风险登记不阻断
MAGNET_STRICT_CHECKS=1 .venv/bin/python docs/skill/data-validation.py   # 严格:风险转失败
.venv/bin/python docs/skill/validate_baseline.py                        # 材料基线比对(改生成器后必做)
.venv/bin/python docs/skill/validate_baseline.py --expect "文件名"       # 只允许指定文件变化
.venv/bin/python docs/skill/validate_baseline.py --update               # 确认后更新基线
.venv/bin/python docs/skill/validate_all.py                             # 统一机审入口
```

**通过标准**:L1–L4 零问题;L5 每条风险必须落到"已声明"(制度里有对应条款)或"须披露"
(写入《异常与待核清单.xlsx》)二者之一——**不允许既无声明又无披露**。

### 环节 4 · 任务说明

> **开工前必读**:`docs/skill/rules1.md` 第 4.2 节(六字段怎么写、预计任务耗时怎么估、附件分类怎么填、
> 任务说明里不要写哪些内容)。

| 字段 | 通用要求 |
| --- | --- |
| 预计任务耗时(分钟) | 只填数字,≥480;覆盖理解、处理、分析、判断、制作交付物、复核的累计有效时间 |
| 业务背景 | ≥60 字:为什么发生、为什么现在做、结果给谁用 |
| 任务目的 | ≥30 字:解决什么问题、支持什么决策 |
| 具体任务要求 | 1–5 条,每条 20–50 字,只写结果不写操作教程 |
| 任务范围与口径 | 只写不写就会改变结论的时间、对象、边界、口径、适用标准 |
| 附件分类 + 交付物要求 | 每个附件标 `非噪音/噪音` 与 `公开/私有`,≥1 个私有;交付物写准文件名与格式 |

**正确性保障**:附件清单与实际文件做一次集合比对(机审核查"任务场景缺少/多出"就是查这个)。
**不得写实际答案、异常名单、金额、行号或评分点**,只能写"允许披露、待补、条件交付、负向结论"这类授权。

### 环节 5 · Query 定稿

> **开工前必读**:`docs/skill/rules1.md` 第 5.1、5.2、5.3 节(七要素、专业领域知识注入的边界、
> 简单 Query 与专业 Query 对比)。

七要素:业务角色与委托关系、核心目标与任务、对象范围与时间、附件使用关系、规则与口径、
缺失与异常处理、交付物。

**正确性保障(闸门 3)**:Query 中每一项都要回材料跑一遍(详见第二篇第 4 步)。

### 环节 6 · 三模型产物与评估表

> **开工前必读**:`docs/skill/rules1.md` 第六章全章(6.1 A/B/C 分工、6.2 A 标准写法、6.3 A 元数据、
> 6.4 可追溯性、6.5 模块 B、6.7 模块 C)。

| 模块 | 要求(training v3.0) |
| --- | --- |
| A 优秀结果标准 | ≥15 条;结果正确性 ≥4、专业质量 ≥4、指令遵循 ≥2、格式 ≥2、语气与沟通 ≥1;任一类型 ≤ 实际总条数 40%;每条写清"依据 + 验收对象 + 合格条件 + 必要边界" |
| B 模型缺点反推 | 关键/重要项中,至少两家"不满足"≥10 条;三家都"不满足"≥6 条;只有一家"不满足"≥1 条;证据写成"原文或具体表现 + 文件名 + 位置" |
| C 敏感红线 | 仅极高敏感(伦理、隐私、政治、色情暴力);计算错误、漏做、格式问题一律不进 C |

**正确性保障(闸门 4)**:三份模型是被要求"识别异常、披露缺失、给负向结论"的独立作答,是最有效的
材料问题探针;模型报出的每条异常都要**回附件逐条复算**,区分"真实材料问题"与"模型误判"——
前者进材料问题清单,后者进该模型的结果评估。

**若材料已冻结、缺口无法修复**:评估表开头必须增加"**材料已知边界与评分处理口径**"一节
(见 `docs/specs/step3-evaluation-rubric.md` 第二节),逐条把材料问题清单里的编号映射到:
① 只验收"是否披露、是否全篇一致、是否给出另一种读法的影响",不验收"选了哪一种读法";
② 材料没有的字段只验收"是否说明无法核验",不要求产物给出该数值;
③ 材料自身的数据特征(舍入、脱敏占位符、已声明的无明细汇总值)不得判为产物缺陷。
同一节还要写明这些宽容口径的**例外**——沉默、混用、编造或把建议写成已批准事实仍按不满足处理。

**硬约束:材料缺口不写入模块 A**。模块 A 只写"优秀结果标准",来源限于 Query、附件与可验证的专业规则;
凡属于材料自身缺陷的内容(如"某字段未定义""某条款未覆盖某情形""某类数据缺失")一律不进模块 A,
否则会把 `input/` 的问题转成对产物的扣分点,导致无法判别模型结果。这类内容统一放在:
前置说明的"材料边界与评分处理口径"(供 A、B 共用)+ 模块 B 的对应评估项(B 模块须写"对应 A 标准"时选「A 未覆盖」并补依据位置)。

**硬约束:评估表的判据只能用题内材料**。每条标准的"依据"只写 Query 与 `input/` 附件(文件 + Sheet/章节 + 字段/条款);
不得把培训材料(`rules1.md`/`rules2.md`)、本项目工具箱(`docs/skill/`)或根目录 `AGENTS.md` 写进评估表——
那些是出题人自己的作业规范,不是判断模型结果的依据。工程类检查(引用格式、条数门槛等)保留在机审脚本与
本项目复盘文档中,不回写进交付给平台的评估表内容。

### 环节 7 · 专家 Solution

> **开工前必读**:`docs/skill/rules1.md` 第 7.3 节(Solution 是什么 / 不是什么、质量要求、
> 与评估表的关系、提交与退回)。

**做什么**:按当前 Query 与附件亲自做一份**可直接交付使用**的成果,并为每个指标写清"公式 + 来源 + 步骤"。

**必须记住的一条**:**Solution 不能用来证明材料没问题**。若 Solution 直接取用附件里已算好的结果列,
而复算用的又是生成器同一套假设,**同源复算必然通过**。对账检查必须与解题路径分离,放进 L5 探针。

## 4. 通用探针库(6 类,换领域时照此选型)

| 类型 | 检查什么 | 通用写法 | 典型触发 |
| --- | --- | --- | --- |
| ① 不变量 | 唯一性、非负、区间、枚举合法、外键存在 | `check(...)` | 主键重复、金额为负、状态值越界 |
| ② 派生一致 | `A = f(B, C)`;汇总 = 明细聚合 | `check(abs(A - f(B,C)) < 容差)` | 毛利 ≠ 净收入−成本;合计 ≠ 分项之和 |
| ③ 跨源勾稽 | 两表/两系统对同一对象应能对上 | 按"对象 + 期间 + 键集合"join 后比度量,超阈值即风险 | 明细 42 件 vs 台账 2 件 |
| ④ 时点与期间 | 期间边界、生效日、截断、跨期 | 按对象 × 期间重算,比较月度分布与最大日期 | 期末退款未入账、生效日落在下一期间 |
| ⑤ 取值可达 | 规则触发后是否真有对象;交付物枚举是否非空 | 按规则反算对象集合,判空 | 某一类处置建议"永远为空" |
| ⑥ 歧义口径 | 同一描述两种读法是否给出**不同答案** | 用两种读法各算一遍,结果不同即风险 | "到期""生效""计入"的时点或范围未定义 |

**探针的通用返回语义(务必统一)**:

```
现象不存在            → ✓ 通过
现象存在 + 制度已声明  → ✓ 已声明可见(条件性交付)
现象存在 + 制度未声明  → ⚠ 记入风险登记(须披露);严格模式转失败
```

**与 ① ② 配套的"来源登记"要求**:每个汇总字段还必须登记来源类别(① 明细聚合 / ② 行内派生 /
③ 原始汇总值)。未登记的字段由 **R-11** 报出,③ 类未声明的字段由 **R-12** 报出——
这样新增一个汇总字段时,脚本会立刻提醒"请说明它从哪来"。

### 6.6 优先记住的六条(最高频)

1. **同一个口径写在多处**(F-23)——只有"不说话的那处"往往是对的;
2. **用 `print` 代替 `check`**(F-21)——看到不等于判定;
3. **结果表不从明细派生**(F-01/F-03)——脱钩之后必然无法复核;
4. **Solution 自证**(F-22)——同源复算必然通过;
5. **交付物枚举取值不可达**(F-19)——规则与材料互斥,某类结论永远为空;
6. **Query 里的主键/示例/时点没人回放**(F-12)——跑一遍 join 就露馅。

| 第 5.2 节 专业领域知识注入 | 新领域有哪些"模型猜不出来"的阈值、资格条件、来源优先级必须由题内给出 |
| 第 6.2、6.3 节 模块 A 与元数据 | 新领域的专业判断会落在五类里的哪一类;类型按"主要失败对象"判定 |
| 第六章模块 B、C | 新领域哪些属于真实缺点(进 B)、哪些属于极高敏感(进 C);该领域的"不应记作缺点"边界 |
| 第七章 状态与退回规则 | 流程未变,但要注意版本差异 |

## 第 1 步:列"关键判断点"

列出交付物真正依赖的专业判断(不是数据字段,而是**判断**)。判断点通常长这样:

"依据什么规则把对象分成几类""什么条件下可以采取某项处置""两个系统的同一笔业务谁为准"。

判据:一个判断点如果不能改变结论,就不必列。

## 第 2 步:填口径唯一性矩阵(闸门 1)

每个判断点一行,回答三问:

| 关键判断 | ① 制度有唯一口径? | ② 材料有对应字段? | ③ 换个人读会不会得出第二种答案? |
| --- | --- | --- | --- |
| …… | 是/否 | 是/否 | 会/不会 |

**第③问"会"的,就是下一道题的返工点**——要么补制度条款,要么在 Query 里写明取哪一种。

**登记与机审**:把每条口径写进 `docs/skill/口径登记.md`(口径 / 制度条款 / 制度关键词 /
Query 关键词 / 评估表关键词 / 备注),然后运行:

```bash
.venv/bin/python docs/skill/validate_calibers.py
```

脚本会打印"口径贯通矩阵":制度关键词缺失、或 Query/评估表该有锚点却没有,都会失败。
本项目 20 条口径的实测覆盖:制度 20/20、Query 20/20(其中 4 条由制度唯一承载)、评估表 20/20(其中 3 条标注无对应标准)。

## 第 3 步:选探针(闸门 2)

按第 4 节的 6 类探针,对每个"应该能对上"的业务关系设计一条探针。选题方法:

- 有两张表描述同一批对象 → **③ 跨源勾稽**;
- 有生效日、账期、期间边界 → **④ 时点与期间**;
- 有"规则触发 → 处置动作"的链条 → **⑤ 取值可达**;
- 制度用了"到期 / 生效 / 计入 / 视为"这类词 → **⑥ 歧义口径**。

每条探针都要写清:比较哪两个来源、用什么键、容忍度多少、超阈值算缺陷还是算可披露异常。

## 第 4 步:做规格可执行性回放(闸门 3)

| Query 中的内容 | 回放动作 | 不通过的表现 |
| --- | --- | --- |
| 跨材料主键 | 真做一次 join,看交集 | 交集为 0,主键形同虚设 |
| 时间基准 | 与制度条款逐字对照 | 两处时点不一致,答案随读法变化 |
| 冲突/口径示例 | 在材料里找出真实对应 | 示例在材料中不成立 |
| 交付物枚举取值 | 反算是否每个取值都可达 | 某一类结论永远为空 |
| 企业专属阈值、来源优先级 | 逐条在制度中找到条文 | 制度缺条款,模型只能猜 |

## 第 5 步:交付物取值可达性(闸门 0 的交付物侧)

把每个交付物的**枚举型字段**列出来,逐一反算是否至少有 1 个对象落入。判定规则:

1. 按制度规则 + 材料数据算出对象集合;
2. 集合为空 → 要么改规则阈值,要么改材料,要么把该取值从交付物要求中删除;
3. 同一字段在不同口径下对象数不同 → 回到第 2 步补口径。

## 第 6 步:写断言集(闸门 0)

把第 1–5 步的结论落成脚本里的 `check()`,例如"至少 N 个对象满足规则 X""至少 1 个对象落入取值 Y"。
断言集是下一道题的第一道防线,改完生成器立刻跑。

## 脚本复用边界

| 组件 | 换领域后 | 说明 |
| --- | --- | --- |
| `check()` / `risk()` / `section()` 骨架、风险登记与 `MAGNET_STRICT_CHECKS` 开关 | **原样复用** | 与本领域无关 |
| `validate_all.py` 统一入口、引用规范检查、A 模块档位机审 | **原样复用** | 只改文件清单常量 |
| 生成器骨架(固定种子、单一事实源、结果表由明细派生) | **复用写法** | 业务逻辑整段重写 |
| L1–L2(字段/公式) | **重写** | 换字段与公式 |
| L3(跨文件勾稽) | **重写** | 换主键与聚合口径 |
| L4(业务合理性) | **重写** | 换量级与相关性判据 |
| L5(跨口径反证) | **按 6 类探针模板重写** | 本项目零售实例见第三篇第 3 节 |
