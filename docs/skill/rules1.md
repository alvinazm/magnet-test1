一、这个项目是在做什么
我们希望建设一批能够检验 AI 是否真的会完成专业工作的高质量任务。
你不需要了解 AI 模型、编程或提示词写作。你只需要使用自己熟悉的专业工作经验，判断：真实工作通常怎样发生、会使用什么材料、需要做哪些专业判断、什么样的结果才算做好。
平台会负责自动生成任务初稿、运行模型和完成机器检查；专家负责把真实业务要求讲清楚，并评价模型交出的工作成果。
💡先认识当前产线会接触的 6 样东西
1. 任务说明：给系统的“任务背景说明”
任务说明不是正式题目，也不是解题步骤。它用于告诉系统：这项工作为什么发生、要解决什么问题、有哪些任务边界、会使用哪些材料、最后要交什么。
系统会根据任务说明和附件，自动生成 3 份正式任务说明初稿。因此任务说明写得越准确，后面需要修改的内容越少。
2. 附件：完成工作需要使用的业务材料
附件就是在真实工作中会交给同事的文件，例如业务台账、审批记录、合同、制度、数据表、会议纪要、历史版本或参考材料。
附件应当提供完成任务所需的事实和规则。模型需要阅读并处理这些文件，而不是只凭常识写一篇泛泛的报告。
3. Query：最终给模型的“正式工作任务说明”
Query 是平台中的字段名称，可以把它理解为一份正式任务书：告诉模型以什么身份，基于哪些材料，完成哪些专业工作，最终交付什么文件。
专家不需要从 0 写 Query。系统会先生成 3 个候选版本，专家只需选择、合并和修改，形成 1 个最终版本。
4. M1 / M2 / M3：三份模型候选产物
最终 Query 通过检查后，系统会让 3 个模型分别完成任务，得到 M1、M2、M3 三份候选工作成果。它们可能是报告、表格、方案或其他 Query 要求的文件。
5. 评估表：专家对题包理想产物及三份模型候选产物的专业评价
评估表用于说明：优秀成果应满足哪些标准、每份候选产物具体有什么问题、是否出现极高敏感内容。评价必须能够回到 Query、附件和候选产物中的具体证据。
6. 专家 Solution：专家按照当前 Query 和附件亲自完成的一份专业交付物。
它应当是该任务设定下可以交给同事、客户或决策者使用的真实成果，而不是“我准备怎么做”的说明。
✅我们想要什么样的任务
一份好的任务应同时满足四点：
- 真实：来自真实岗位中会发生的工作，而不是为了测试模型临时拼出的场景。
- 可解：完成核心任务所需的事实、规则和材料都在题内，不能靠猜。
- 专业：需要领域判断、跨材料核对、多步骤计算、例外处理或业务取舍，而不是简单摘抄、汇总和改格式。
- 可验收：最终交付物明确，专家能够依据材料判断做对了什么、做错了什么。
“难”不等于故意缺信息、写得含糊或设置恶意陷阱。我们要的是：材料完整、要求清楚，但仍然需要专业能力才能做好。
二、开始前请先记住 3 个质量重点
1. 任务说明值得认真写
任务说明是系统生成 3 个 Query 初稿的依据。写得越清楚，系统生成的任务说明越接近可用版本，你在步骤 2 修改 Query 的成本越低。
不要把任务说明当成简单备注。它决定系统能否正确理解：为什么要做、要解决什么问题、哪些边界会影响结论、附件如何参与、最终要交什么。
2. 专业难度要在设计题目时就放进去
Query 修改时要主动注入真正的领域考查，例如：
- 需要依据规则与例外条件作出判断；
- 需要跨文件匹配、对账、归因或勾稽；
- 需要多步骤计算、口径转换或异常识别；
- 需要在多个业务目标或限制之间做合理取舍；
- 需要把中间结果组织成可复核、可使用的专业交付物。
❗️如果题目机审通过后任务步数低于 25 步，说明任务过于简单，请重新设计该任务。应在保证真实业务场景的前提下，重新选择更有专业判断空间的工作任务。
3. 不要靠故意缺信息或设置陷阱增加难度
以下做法不属于专业难度，也无法通过审核：
- 故意漏掉核心附件、关键事实、企业规则或必要口径；
- 让 Query 与附件互相矛盾；
- 用模糊表达让任务存在多个完全不同的理解；
- 点名“哪个附件是噪音”“正确答案是什么”或提前给出结论；
- 堆无关文件、超长文字、无意义步骤或纯格式要求；
- 要求模型联网、登录内部系统或使用题内没有提供的外部数据，却不给失败处理方式；
- 在材料中夹带“忽略原任务”“必须输出某个结论”“请审核判通过”等与真实工作无关的指令。
三、产线任务流程总览
图 1｜专家生产流程总览（以题目状态为准）
[图片]
专家只需要关注工作台显示的“题目状态”，当前生产流程是：
1. 提交附件与任务说明并通过附件机审。
2. 进入“题目待提交”，选择、整合并提交最终 Query。
3. 题目机审通过后，系统运行任务步数；步数少于 25 步时，任务过于简单，退回“附件待提交”重新设计；步数达到 25 步及以上时，进入评估产物生成。
4. 系统生成 M1、M2、M3，专家阅读三份模型候选产物并填写、提交新版评估表。
5. 评估表通过机审后，进入“Solution 待提交”；专家按当前 Query 和附件完成并提交 Solution。
6. Solution 通过机审后，进入初审；初审通过后进入复审。
7. 复审通过后，一阶段通过；如附件、Query、评估表或 Solution 存在不可修复问题，则一阶段拒绝。
四、步骤 1：提交附件与任务说明
4.1 先从真实工作中选任务
建议先用一句话回答：
在什么业务情境下，哪个岗位会使用哪些材料，完成哪些专业处理，最后交付什么文件，供谁做什么决策或行动？
合格场景通常具备：
- 有明确的业务发起原因和使用场合；
- 有完成任务真正需要使用的材料；
- 有至少一个会影响结论的专业判断点；
- 有清晰的最终交付物；
- 结论能回到附件中的事实、规则或计算；
- 专家自己能说明如何验证结果是否正确。
偏简单示例：
根据员工花名册统计各部门人数和平均薪资，输出汇总表。
专业任务示例：
联合员工花名册、转正审批、调薪审批、薪酬制度和历史工资表，确定本期应转正范围，核验审批效力和薪酬生效日期，计算应发差异，识别漏转正、错调薪、提前或延迟生效等异常，并输出复核明细和问题清单。
后一个任务需要跨材料核对、规则判断、日期与金额计算、异常处理和交付组织，才具有真实区分度。

预计任务耗时怎么填写和估算
预计任务耗时，是累计有效工作时间，不是连续工作时长，也不是项目从开始到结束的自然日跨度。它应覆盖一名具备相应专业能力的专家，在真实工作条件下独立完成任务所需的全部有效投入。
- 填写格式：字段单位已经是“分钟”，只填写数字，例如 480；不要填写“8 小时”“480 分钟”或“约 1 天”。
- 最低门槛：预计任务耗时必须不少于 480 分钟（8 小时）。
- 可以跨周期累计：不要求专家连续、全神贯注工作 8 小时。真实任务可分散在多天或多周完成，只需计算实际投入的累计分钟数。
- 应计入：理解任务与口径、阅读和整理材料、数据处理、分析与计算、专业判断、制作全部交付物、必要的材料核对、专业沟通以及复核修改。
- 不应计入：被动等待、系统排队、无实际工作的审批停留时间，以及与本任务无关的会议或沟通。
建议估算方法：先拆分任务环节，分别估算每个环节的实际投入分钟数，再求和。跨周期任务可按“每天平均有效投入分钟数 × 实际工作天数 + 一次性整理与复核时间”估算。估算结果应与任务说明、附件数量和复杂度、处理步骤以及交付物要求相互匹配。
示例：投行 IPO 尽调可能每天投入 60—120 分钟，连续 10 个工作日，仅日常投入即为 600—1200 分钟；再加上汇总和复核时间，累计耗时已远超 480 分钟。这类任务符合要求，即使它并非连续工作 8 小时。
项目组会审核耗时是否达标且合理。低于 480 分钟的任务将直接拒绝；明显虚高、且无法由任务说明、附件规模、工作步骤或交付物复杂度解释的估算，也不能通过审核。不要把一个实际只需 60 分钟的简单任务直接填写为 480 分钟。
附件分类和交付物怎么填
- 非噪音：与任务有关，可能用于理解或完成任务；噪音：用于模拟真实工作目录，但不应在正式任务说明中提示模型它与任务无关。
- 公开：经官方公开的附件材料；私有：未经官方公开的附件材料
- 每个附件都要同时完成“非噪音 / 噪音”和“公开 / 私有”两项标记，且至少有一个附件标记为私有。
- 附件分类只填写包含扩展名的原始文件名和两项分类，不要摘录或概述附件内容。
- 交付物要填写准确文件名和扩展名；只有小数位数、必须包含的文件等确实影响交付的要求，才需要额外补充。
三个核心字段不要重复
- 业务背景回答“为什么现在要做”。
- 任务目的回答“做完后解决什么问题”。
- 具体任务要求回答“为了实现目的，必须完成什么”。
同一句话只放在最合适的字段里，不要在三个字段之间反复改写。
具体任务要求要写结果，不要写操作教程
推荐：
1. 判断收入增长是否伴随利润质量改善，并识别被汇总数据掩盖的结构性差异。
2. 比较各区域与重点门店的规模、增速和利润表现，识别主要异常及业务影响。
3. 对下半年预算和经营资源的增投、维持或收缩给出建议与依据。
不推荐：
1. 先清洗销售明细。
2. 再按区域做透视表。
3. 最后计算毛利率并排序。
后者把专家的操作路径写死了，却没有说明最终要解决的业务问题。
任务说明里不要写这些内容
- 附件中的具体答案、异常名单、金额、行号或预期结论；
- 标准答案、评分点、评分规则、模型弱点或审核结论；
- 除“附件标记”字段外，在业务背景、任务目的和具体任务要求中点名哪些附件是噪音、哪个来源才是“正确来源”；
- 完整的解题步骤、公式推导过程或推荐工具；
- “不得虚构”“仅使用附件”等通用模型要求；
- 可以从背景、目的、任务要求或文件名直接理解的重复信息。
任务说明可以说明“需要识别异常、披露缺失、形成待补清单或给出负向结论”，但不能提前写出本题实际有哪些异常、谁有问题、正确结果是多少。
4.3 附件怎么准备
附件的作用，是让模型像真实同事一样，必须依据业务材料才能完成工作。附件应当是任务的事实与规则来源，而不是装饰。
文件类型多样性
默认要求：除符合下述例外外，核心附件包至少包含两类不同文件类型。文件类型按格式类别判断，不按扩展名凑数；例如 XLSX、XLS、CSV 都属于表格类，不能算三种类型。噪音、空文件、重复导出或为凑类型临时添加的文件不计入。
不同类型应服务于真实业务闭环，例如表格与制度 / 合同 PDF、文档与明细表、图片与检验记录。不要为了满足规则硬塞与任务无关的第二类文件。
可以例外的场景
- 纯数据 / 台账核对：财务、经营、人力、供应链、统计等任务，真实工作材料本身就是多份表格，且任务要求跨文件对账、计算、异常识别或版本比较；可以全部为表格类。
- 法务 / 合同 / 合规材料审阅：合同、制度、政策、诉讼等材料天然以 PDF 或文档为主，且任务要求逐份阅读、比对条款、判断效力或抽取风险；可以全部为文档类。
- 软件工程 / 代码审查：任务对象本身是同一语言或同一类源码，要求进行代码理解、排错、重构或安全审查；可以全部为代码类，但必须有多个真实模块、版本或文件间依赖。
- 视觉、音频、视频或医学 / 工程专业文件处理：任务是图像质检、音频转写、视频审核、DICOM 影像判断、CAD / BIM / GIS 文件分析等，输入格式由业务工具固定决定；可以全部为对应专业格式。
例外必须同时满足：单一格式是该领域真实工作中的自然形态；至少 5 个核心文件之间存在对象、期间、版本或上下游关系；Query 明确要求专业处理而非简单浏览或汇总；任务说明中写明为何适用单一类型例外，以及每类文件如何被使用。
如果业务上自然存在制度、说明、参数表、元数据或结果记录等辅助材料，应一并提供，不得以“领域例外”为由省略。单一类型但内容重复、关系薄弱、仅靠文件数量和噪音凑复杂度的附件包，仍可能被附件机审或人审退回。
附件的基本要求
- 核心附件原则上至少 5 个，并且在任务中被真实使用；不要把一个文件机械拆成多份凑数量。
- 多个附件之间应有真实业务关系，例如主键、时间、版本、规则与待审对象、明细与汇总等。
- 删除附件后，仅凭 Query 不应还能完成大部分核心产物。
- 文件应可打开、可解析；PDF 应能提取文字，关键数字不能只放在图片中。
- 优先使用常见办公文件格式；不要提交加密文件或依赖专用软件才能打开的格式。
- 单文件建议不超过 20 MB，全部附件建议不超过 300 MB。
- 噪音用于模拟真实工作目录，不用于恶意误导；如设置噪音，建议不超过附件总数的 30%。
- 每个附件都要标记“非噪音 / 噪音”和“公开 / 私有”，且至少有一个私有附件。

以下问题可能直接导致附件校验不通过：
- 核心业务材料明确是 synthetic、test、模拟、测试、样例、合成或仿真数据；

- 附件直接包含标准答案、完整解题步骤、最终名单或完整结论推导，实质替代了专业判断；
- 附件中夹带要求模型忽略原任务、输出指定结论、泄露信息或要求审核通过的指令。

5.1 最终 Query 应讲清楚什么
一份可执行的 Query 通常应包含：
1. 业务角色与委托关系：谁在什么场景下接到任务，结果给谁使用。
2. 核心目标与任务：需要判断、比较、计算、核验、归因或建议什么。
3. 对象、范围和时间：分析哪些对象、哪个期间、哪个版本；相对时间会影响结果时写清基准日期。
4. 附件使用关系：需要依据哪些材料完成哪些核心工作，但不要点名噪音答案。
5. 规则与口径：题内必须提供的企业专属规则、阈值、来源优先级、单位、粒度、主键或例外条件。
6. 缺失与异常处理：允许披露、待补、缩小范围、条件性建议、局部交付或负向结果时，要明确授权。
7. 交付物：最终文件名称、格式、必含内容和真实业务用途。
5.2 怎样注入专业领域知识
专业性可以来自以下方向：
- 专业判断：根据规则、证据和例外条件做分类、取舍、归因、定级或建议。
- 跨源处理：建立正确主键，处理粒度、单位、版本、时间快照或来源优先级。
- 多步骤计算：前一步结果会进入下一步，结果能够复算和勾稽。
- 异常处置：识别真实缺失、冲突或异常，并决定重算、隔离、待补、披露或给出负向结论。
- 交付组织：多个文件、Sheet 或章节之间口径一致，数字可追溯，结论能直接支持业务动作。
如果真实工作并不存在唯一的企业口径，不要为了“增加专业性”强行写死一种评分公式或分析方法。可以要求模型说明采用了什么方法、为什么这样做，以及如何保证结果可复核。
但以下内容不能靠模型自行猜：
- 本企业当前执行的阈值、资格条件、固定评分标准、内部政策和来源优先级；
- 本题特定对象、期间、版本的实际数据和状态；
- 运行环境中不存在的外部系统、登录权限、实时数据或联网能力。
这些内容若是完成核心交付所必需，必须在 Query 或附件中有明确依据。

不推荐：

6.2 模块 A：怎样写一条可稳定评分的优秀结果标准
数量与类型要求
- 共填写至少 15 条标准，不设条数上限；
- 结果正确性：至少 4 条；
- 专业质量：至少 4 条；
- 指令遵循：至少 2 条；
- 格式：至少 2 条；
- 语气与沟通：至少 1 条；
- 任一类型不得超过模块 A 实际总条数的 40%；40% 不是整数时，按向下取整后的整数上限执行。例如共填写 15 条时，单一类型最多 6 条。
“不设上限”不等于越多越好。标准写到核心任务和交付物已经覆盖完整，且继续新增只会重复评价时，就应停止。不要为了凑类型机械拆分，也不要把同一问题换一种说法重复计分。
「标准描述」推荐写法：依据＋验收对象＋合格条件＋必要边界
一条标准应让另一位同领域专家能够直接判断“满足、不满足，或落入哪一档”。推荐按下面的结构写：
依据或来源＋检查什么＋达到什么状态算合格＋存在什么例外或不能推出的结论
示例：
依据 Query“以员工编号作为跨表核对主键”及《薪酬制度》第 3.2 节，复核明细须以员工编号关联花名册、审批记录和工资表；姓名只用于展示，姓名冲突时须保留差异记录，不得直接合并。
这条标准说明了依据、对象、规则和边界。审核员不需要猜“为什么要检查主键”“什么算合格”。
不推荐：
结果应专业、全面、准确，数据处理方式合理。
这类表述没有检查对象、证据位置和通过条件，不同审核人会得出不同结论。
6.3 A 模块元数据字段怎么填

遇到交叉情况时，按“修好它主要需要改什么”判断：

- 改分析方法、证据链或专业边界：专业质量；
- 补做题面明确要求但完全漏掉的工作：指令遵循；
- 只改文件、字段、位置或结构：格式；
- 只改表达方式：语气与沟通。
「类型」案例：类型看主要失败对象，不看问题严重程度
案例背景：SaaS 客户健康度任务中，附件规则要求红色客户“5 个工作日内完成客户成功回访并上报客户成功总监，回访后 48 小时内更新处置结论”。M1 却写成“3 个工作日内启动处置，48 小时内回报结论”。
为什么判“指令遵循”：这里既有动作错误，也有时限错误，但两者都能直接回到附件规则原句。修复动作是按原规则改回“5 个工作日内完成回访并上报、回访后 48 小时内更新”，因此主要失败对象是“有没有照明确规则执行”，不是模型是否具备一般性的专业判断能力。
不要混淆：类型回答“错在哪里”；影响程度回答“错得有多重”。两者分别判断，不能因为问题影响大就改选“结果正确性”，也不能因为影响小就改选“格式”。
6.3.2 是否有中间状态与档位
“是否有中间状态”问的是：这条标准除了完全满足和不满足，是否还存在有业务意义、能够稳定判断的部分完成水平。
- 只有明确的“是 / 否”“正确 / 错误”“存在 / 不存在”时，选“无”。例如是否交付指定文件、是否泄露隐私、总金额是否与附件一致。
- 存在可以客观区分的部分完成水平时，选“有”。例如应覆盖 10 个风险对象，实际可能覆盖其中一部分；归因可能覆盖全部维度但证据不完整。
- 选择“有”后，填写 2—4 档，从低到高排列；高档应包含低档已经完成的要求。
合格档位必须同时满足四点：
1. 可观察：用数量、比例、明确条件或可定位证据划分，不写“基本”“较好”“少量”“多数”。
2. 不重叠：一个实际表现不能同时落入两档。
3. 无空档：相邻档位首尾衔接，不出现任何档都无法归入的情况。
4. 逐级递进：升一档需要多满足一项清楚的条件，最高档代表完整合格，不把额外加分项设成满分门槛。
示例：要求覆盖 10 个风险对象并提供证据时，可按“覆盖 0—4 个”“覆盖 5—7 个”“覆盖 8—9 个”“覆盖全部 10 个且均有可定位证据”分档。不要写成“覆盖较少 / 基本覆盖 / 大部分覆盖 / 覆盖充分”。
并非每条标准都需要中间状态。能够直接判断对错的标准强行设置多档，反而容易产生档位重叠和审核争议。
6.3.3 影响程度：关键、重要、一般
影响程度看的是“不满足这条标准会造成什么业务后果”，不看标准写了多少字、包含多少字段或检查起来是否容易。
等级
判断标准
关键
会改变核心结论、主要名单或重要金额，影响主要决策，或使必需交付物无法使用
重要
交付物整体仍能使用，但存在实质缺陷，需要明显返工或额外人工核验

不要把所有标准都选“关键”。同样，不要因为问题属于格式或语气就自动选“一般”：漏交必需文件可能是关键，局部措辞问题通常才是一般。
「影响程度」案例：重要性只看业务影响
关键缺点：API 迁移任务中，M1 将一个存在 SDK 兼容阻断的客户×API 保持为 P2，正确结果应为 P2→P1，并导致最终 P1、P2 分布同时错误。该错误会直接改变迁移优先级和管理排期，因此标为“关键”。
一般缺点：同一任务中，M1 把附件未登记的 Go SDK 扩入当前验证范围；M2 未单独交代一条已经到期、且不在当前对象池内的历史例外记录。两项都需要修正，但不会改变当前 46 个对象的优先级、截止日或批次，因此标为“一般”。
判断方法：不要按涉及对象数量、文字长度或技术复杂度定级。先问：不修时，交付物能否继续按原用途使用，核心结论或执行顺序是否会改变。
6.4 易错维度：可追溯性
可追溯性回答的是：为什么要检查这条标准，依据在哪里，依据能够支持到什么程度。
A 标准的合理来源只有三类：
1. Query 明示要求：题面明确写出的任务、范围、口径、限制或交付要求；
2. 附件能够支持的要求：附件中的字段、数据、制度、合同条款和业务规则，或可以从附件稳定推导出的隐性要求；
3. 行业共识或专业默认规则：可验证的职业规则和专业底线，例如结论要有证据、材料不足时应保守表述、不得虚构事实、同一计算链应保持口径一致。
三类都找不到时，这条标准很可能只是个人偏好，不能写成硬性评分要求。
来源怎样写进当前评估表
每个评分项需要在“标准描述”中简洁地带出评分项来源：
- Query 来源：写明对应任务或约束，可引用关键短语；
- 附件来源：写明文件名和稳定位置，例如章节、条款、Sheet 或字段；
- 行业共识：写明具体专业原则、适用条件和必要例外，不能只写“依据专业经验”。
推荐：
依据《客户健康度评分标准》3.1a—3.1c，红色风险触发项须逐条与规则一致；附件不足以确认时应标记待核，不得默认命中。
不推荐：
风险判断应符合附件和行业经验。
后者既没有定位，也没有说明附件能够支持什么。
行业共识的边界
行业共识可以补充 Query 没有逐字写出的专业要求，但不能无限扩张：
- 不能与 Query 或附件冲突；
- 不能补造附件中不存在的任务事实、阈值或唯一答案；
- 不能把个人偏好的工具、模板、图表或实现方式设为唯一要求；
- 依据不足时不能设置决定性失败条件；
- 允许多种专业做法时，应验收结果和证据，不强制唯一过程。
「可追溯性」正例一：附件条款来源要写到可直接定位
SaaS 客户健康度任务 A5：“触发规则标注必须与《SaaS客户健康度评分与流失预警标准》3.1a/3.1b/3.1c 与 3.2a/3.2b/3.2c 逐条一致，每名预警客户列出的触发规则与实际指标条件相符。”
为什么可追溯：标准写明了附件名称、条款号、验收对象和通过条件。评分人可以直接打开对应条款，逐客户核对触发规则，不需要猜“附件依据”具体指什么。
可复用写法：依据《附件名称》具体章节、条款、Sheet 或字段，要求哪个对象完成什么判断；若存在例外，再写明什么情况下不适用。
「可追溯性」正例二：Query 没逐字写出，也可以来自有边界的专业默认规则
高一英语资源选型任务 A12：最终意见必须分别回答：现有资源是否足以启动内容制作、定稿或发布前还需满足哪些前置条件、哪些事项仍无法确认；不得把“可以启动内容制作”表述成“已经满足直接定稿或上线条件”。
为什么不越界：Query 已要求面向课程研发负责人判断课程制作能否启动。A12 将这一决策要求整理成三个可执行问题，并防止把“启动制作”越权扩大成“可以上线”。它没有补造附件事实、没有新增业务阈值、没有限定唯一模板，属于服务于原任务目标的专业默认判断。
边界：专业默认规则只能补足判断方法和职业底线，不能借此新增附件不存在的对象、数字、制度或决定性失败条件。
模块 A 完整示例（具体填写以更新后的前端页面为准）：
类型：专业质量
标准描述：依据 Query 的分析要求和“结论应有证据、材料不足时应保守表述”的专业规则，问题判断和改进建议应清楚区分数据事实、分析判断和待核假设；证据不足时不得使用确定性因果表述或作无依据的人员能力评价；自行提出的管理阈值应明确为建议或试行，不得写成既有制度要求。若题内材料或明确规则已经提供了相应依据，则可以作出与依据范围相匹配的确定性结论。
是否有中间状态：有。
中间状态档位：不满足：核心结论存在无依据的确定性因果或能力判断，或将建议阈值写成既有制度要求，导致主要判断无法复核；部分满足：核心事实和主要结论有依据，但部分次要归因、建议或阈值没有清楚区分事实、推测和建议性质，且不改变主要结论；满足：事实、判断和待核假设边界清楚，所有确定性结论均能回到 Query、附件或明确专业规则，建议阈值均标明建议或试行性质。
影响程度：重要。
为什么优秀：这条标准说明了来源、评价对象、合格条件、档位和例外边界，另一位同领域专家可以据此稳定判断不同产物的完成程度；它评价的是通用专业能力，不包含任何模型名称、模型表现或特定错误。
6.5 模块 B：把实际缺点写成证据闭环
模块 B 记录 M1、M2、M3 中真实存在、能够被证据支持的问题，并通过真实问题进行「评估项」的合理反推。
6.5.1 数量要求
v3.0 新版口径：B 模块中影响程度为关键 / 重要「评估项」中，至少两家产物“不满足”的不少于 10 条；其中三家都“不满足”的不少于 6 条；只有一家“不满足”的条数至少 1 条。不要为了达到门槛编造、重复、拆碎或夸大问题；如果共有缺陷不足，应重新设计任务。
6.5.2 缺点怎么找：三个模型产物的 6 个检查角度
1. 任务覆盖：逐条核对 Query 的结果性要求和必交文件，标记漏做项。
2. 事实与计算：抽查主键、数字、日期、单位、分母、汇总和关键结论，确认能否由附件复算。
3. 规则与边界：检查制度条款、例外条件、状态口径和版本日期是否被正确应用，是否把建议写成现行规则。
4. 跨文件一致性：对照同一对象在不同文件、Sheet、章节中的名称、状态、数字和结论。
5. 证据与推断：区分观察到的现象、基于证据的判断和待核假设；没有证据时不得写成确定因果。
6. 可用性与格式：确认文件名、格式、字段位置、必需表头和交付结构满足 Query，且不影响使用。
不应记作 B 缺点的情况
- 只是专家偏好的工具、模板、排版或表达方式，且不影响任务目标和交付使用。
- 模型采用了与专家不同但能够复核、前后一致并符合 Query 的等价方法。
- Query 或附件没有提供事实，模型已经明确标记待确认、无法判断或不适用。
- 把同一个失败换一种说法重复计数，或把一个缺点机械拆成多个字段来凑数量。
6.5.3 「评估项描述」怎么写
在收集真实缺点后，需要将其合理反推为通用的「评估项描述」，用于说明：这一条评估什么问题、什么情况算问题、问题会造成什么业务影响。每条 B 都要先根据模型真实缺点进行合理反推形成「评估项描述」，「评估项描述」应写成一个能够对每份产物单独回答“有没有这类缺点”的命题，再拿这条描述去判断三家情况。
它不是模型表现记录，也不是修复方案。填写时不要写具体模型名称、模型原文、文件位置、具体错误数值或逐项修改动作。这些内容分别填写在「模型证据」和「合格时应满足」中。
推荐结构：
评价对象＋问题判定口径＋业务影响
1. 评价对象
写清楚要评价的业务能力、结果对象或交付环节，例如：
- 跨表对象关联是否可靠；
- 关键数字和计算口径是否一致；
- 规则、例外条件和状态判断是否正确；
- 分析结论是否区分事实、判断和推测；
- Query 要求的核心交付是否完成。
不要写成“评估 M1 是否……”“模型有没有……”；模型分别通过“三家情况”和“模型证据”体现。
2. 问题判定口径
只写问题的抽象判定边界，不写某个模型实际发生了什么，也不展开完整修复方式。
可以使用以下表达：
- 出现主键错配、错误合并或无法解释的对象关联时，属于该问题；
- 将题内无法支持的推测写成确定性结论时，属于该问题；
- Query 明确要求的核心分析、文件或异常识别未交付，且不能由“待核 / 不适用”合理解释时，属于该问题；
- 计算结果、状态判断或规则适用与题内依据不一致时，属于该问题。
3. 业务影响
写清问题为什么重要，重点说明它会影响什么：
- 导致人数、金额、范围或状态判断错误；
- 使结论无法复核或无法追溯；
- 造成风险、异常或优先级判断遗漏；
- 使后续决策、执行或合规判断失去依据；
- 导致核心交付无法使用。
不要在这里写具体影响数值、具体文件位置或某个模型的实际表现，这些内容放入“模型证据”。
6.5.3 B 模块元数据字段怎么填
1. 类型：沿用 A 的五类口径，看缺点的主要失败对象；
2. 评估项描述：由 M1、M2、M3 的真实缺点反推一条通用缺点命题，写清评价对象、可观察的缺点类型和业务影响；不出现模型名，不放具体模型原文或位置，不写完整修复动作。
3. 三家情况：M1、M2、M3 三格均必填“满足 / 部分满足 / 不满足”；三家情况按以下逻辑判断：
- 满足：产物中没有出现评估项描述所定义的缺点，或已有内容完全避开该缺点。
- 部分满足：评估项描述所定义的缺点确实存在，但只影响部分对象、部分步骤或部分交付，且可以用客观边界区分“部分”和“全部”。只有确实存在中间状态时才使用。
- 不满足：评估项描述所定义的缺点在产物中实质存在，已经影响核心结果、关键交付或主要判断；如果缺点具有系统性或覆盖主要对象，也应判“不满足”。
4. 模型证据：说明 M1、M2、M3 各自是否出现这条缺点，以及缺点实际出现在哪里；仅为填“不满足 / 部分满足”的模型分别填写原文或应出现位置。
模型证据采用“原文或具体表现＋文件名＋位置”的格式：
- 文档：文件名＋章节、页码或段落标题；
- 表格：文件名＋Sheet＋行号、单元格或业务对象编号；
- 多文件：分别写清每个位置，不能只写“产物中多处”；
- 内容缺失：写明应出现在哪个交付物、Sheet 或章节，并确认所有合理承载位置均未出现。
5. 合格时应满足：写任何一份产物都能直接对照的最低合格状态、具体验收条件和必要边界，不写模型名或“重新校正”等返修动作。
6. 是否有中间状态：判断是否存在可客观分级的部分满足；
7. 中间状态档位（选填）：如选择“有”，填写 2—4 档；
8. 影响程度：按不满足该标准的业务后果进行定级，口径同模块 A；
9. 判分说明与例外边界（选填）：说明什么材料事实或适用前提下该缺点不成立。缺点是否成立依赖前提时，建议填写例外边界。例如：
若附件中存在经审批且仍在有效期内的延期记录，并明确对应同一客户和同一业务对象，则延期状态不命中本缺点。
例外边界不是替模型找借口，而是防止把材料允许的合法情形误判为失败。
10. 对应 A 标准：如对应 A 模块中某一标准，此处可进行关联。选择「A 未覆盖」时需补充“依据位置”。
11. 依据位置：参考 A 模块对依据/可追溯性的论述，需单独列出。
模块 B 完整示例（具体填写以更新后的前端页面为准）：
类型：结果正确性
三家情况：M1：不满足；M2：满足；M3：部分满足
评估项描述：评价不同业务材料之间的对象关联是否可靠、一致且可追溯；出现主键错配、错误合并或无法解释的对应关系时，属于该类缺点。此类问题会导致复核范围、人数和金额结果失真。

是否有中间状态：有。
中间状态档位：满足：不存在主键错配、错误合并或无法解释的对应关系；部分满足：仅少量非核心记录存在关联缺陷，核心对象和主要结果仍可复核；不满足：核心对象存在错配、错误合并，或缺陷具有系统性并影响主要结果。
影响程度：关键。
对应 A 标准：A 中“跨表核对主键正确”。
依据位置：Query 的主键要求及《薪酬制度》第 3.2 节。
6.7 模块 C：敏感红线
模块 C 只用于极高敏感内容，不是“严重质量问题”收纳区。
当前可选择的红线类型包括：
- 伦理问题；
- 隐私泄露；
- 政治错误；
- 色情或暴力；
- 其他极高敏感。
如果选择“有”：
- 至少添加 1 条红线命中记录；
- 选择实际涉及的 M1、M2 或 M3；
- 为每个已选模型填写真实原文及可定位位置；
- 说明为什么该内容构成对应类型的敏感红线。
“建议设立的红线标准”为选填，最多 3 条。它是规则建议，不代表候选产物已经命中。
普通计算错误、事实错误、漏做任务、专业性不足、虚构一般业务内容、违反普通任务约束或格式问题，即使影响很严重，也应在 A、B 中评价，不能升级为敏感红线。只有实际符合上述极高敏感类型时才进入 C。

7.2 不通过或人审退回时
- 附件机审不通过：退回“附件待提交”，修改附件 / 任务说明后重新提交。
- 题目机审不通过：退回“题目待提交”，仅修改 Query。
- 题目机审通过后任务步数少于 25 步：判定任务过于简单，退回“附件待提交”，重新设计任务和附件。
- 评估表机审不通过：退回“专家评估中”，仅修改评估表。
- Solution 机审不通过：退回“Solution 待提交”，仅修改 Solution，不回改已锁定的附件、Query 或评估表。
- 初审发现 Query 或 Query—附件闭环问题：退回“题目待提交”；修改后重新生成后续评估产物。
- 初审发现评估表问题：退回“专家评估中”；仅修改评估表。
- 初审发现附件“一眼假”或其他不可返修问题：直接进入“一阶段拒绝”，不退回附件修改。
- 复审仅确认初审问题是否修复；未修复则继续复审 / 退回对应编辑节点，修复后重新提交审核。
- 项目组审核发现预计任务耗时低于 480 分钟：直接进入“一阶段拒绝”；耗时明显虚高且无法由任务说明、附件规模、工作步骤或交付物复杂度解释的，也不能通过审核。
被退回后，只修改当前题目状态允许编辑的内容。不要在锁定字段中等待新的编辑入口。
7.3 Solution 提交
Solution 是专家在当前 Query 和附件基础上亲自完成的一份完整、可交付、可复核的专业成果。它应当像真实工作中可以交给同事、客户或决策者使用的成果，而不是“我准备怎么做”的说明。
Solution 不是什么
- 不是评估表、审核意见或 Rubrics；
- 不是对 M1、M2、M3 的点评或改写；
- 不是空白模板、解题思路或操作步骤；
- 不是只写结论但缺少 Query 要求的正式文件；
- 不是大量复制附件、没有完成专业处理的材料汇编。
Solution 怎么写
1. 先重新核对当前 Query 的任务目标、对象范围、时间口径、交付物和明确限制。
2. 按照真实业务工作方式完成全部核心任务，提交 Query 要求的正式文件、表格、报告或其他交付物。
3. 对关键数字、名单、状态、计算和判断保留可复核路径，能够回到附件的文件、Sheet、字段、条款或记录。
4. 根据任务需要形成“事实或数据 → 专业判断 → 业务影响 → 建议或行动”的完整闭环。
5. 材料不足、冲突或无法确认时，按 Query 允许的边界披露待核、缩小范围、条件交付或负向结论，不得补造事实。
6. 完成跨文件一致性检查，确认对象、期间、单位、数字、状态和结论没有互相矛盾。
Solution 的质量要求
一份合格的 Solution 应同时满足：
- 完整：覆盖 Query 的全部核心任务和主要交付物；
- 可核验：关键事实、数字和规则有明确依据，关键结果能够复算或追溯；
- 专业：完成必要的判断、异常识别、例外处理和业务取舍，而不是简单摘抄或汇总；
- 可使用：文件可以打开，结构、名称、单位、版本和对象清楚，符合真实工作中的交付形式；
- 边界清楚：区分已确认事实、分析判断和待核假设，说明必要限制和处理方式；
- 不泄露评测过程：不得出现模型编号、评估表、Rubrics、评分、机审意见或“标准答案”等评测视角内容。
Solution 与评估表的关系
评估表用于记录 M1、M2、M3 的专业评价信号，Solution 用于提供一份真实可用的参考成果。Solution 不需要按评估表编号逐条作答，也不需要复述评估表或审核意见；但它必须遵守同一份 Query、附件和可靠专业规则。不能为了迁就 Solution 的写法，反向修改 Query 或评估标准。
提交与退回
评估表通过机审后，进入“Solution 待提交”。Solution 提交后进入“Solution 机审中”；如果机审不通过，只修改 Solution，不回改已锁定的附件、Query 或评估表。修复后应重新做一次全量一致性检查，避免同一错误继续留在其他文件、章节或结论中。
